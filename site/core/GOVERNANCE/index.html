    Životní cyklus změny (Workflow)

    Každá změna v projektu musí následovat tento cyklus, aby byla zaručena důvěryhodnost a integrita SSOT.

    sequenceDiagram
    participant A as AI Agent
    participant S as Scripts (Inventory)
    participant L as Linters (Vale/MD)
    participant U as User (Review)

    A->>S: Spustit inventuru (Před změnou)
    S-->>A: Report stavu projektu
    A->>A: Vložit chybu (RED PHASE)
    A->>L: Spustit linter
    L-->>A: Detekce chyby (Důkaz kontroly)
    A->>A: Implementovat opravu (GREEN PHASE)
    A->>L: Spustit linter
    L-->>A: PASS (Důkaz opravy)
    A->>U: Notify User + Walkthrough

    Provozni pravidla

    1. Pred refactoringem dokumentace spustit inventuru.
    2. Pri kritickem FAIL nejdriv opravit infrastrukturu.
    3. Zmeny ridicich dokumentu delat po davkach (P0 -> P1).
    4. Po kazde davce aktualizovat canonical docs_control/next_session.json (+ docs_control/next_session_note.md) a regenerovat view.

    Vychozi operacni princip (globalni)

    Pri navrhu a implementaci pouzivat vychozi rezim: deterministicka kvalita + efektivita.

    To znamena:

    1. Nejdriv state discovery (realita, ne predpoklady).
    2. Tvrde poradi pro zmenu je indexace/preflight -> rozhodnuti -> zmena (nikdy opacne).
    3. Pred kodovanim uzamknout scope + acceptance.
    4. Delat nejmensi plne funkcni end-to-end slice.
    5. Kazdou zmenu mit validovatelnou (schema, validator, alignment, stale-check).
    6. generated artefakty neupravovat rucne.
    7. claim = evidence (zadne "hotovo" bez cerstveho dukazu).
    8. Po zmene synchronizovat SSOT + generated view.
    9. Pri procesni odchylce pouzit freeze -> navrat k poradi.

    Pravidlo archivace souboru

    1. Aktivni/SSOT soubory zustavaji se stabilnim nazvem.
    2. Archivni kopie pouzivaji format nazev-YYYY-MM-DD--HH-mm.md.
    3. Odkazy i skripty miri na stabilni (nearchivni) nazvy.
    4. NEXT_SESSION se archivuje do NEXT_SESSION_Archive/.
    5. Nova session NEXT_SESSION se vytvari pouze pres scripts/archive_next_session.ps1 -ResetAfterArchive.
    6. Pred vytvorenim nove session musi byt vyplneny blok: Neprovedeno, Rozpracovane, Provedeno, Poznamka.

    Markdownlint scope policy (blocking + backlog)

    1. blocking scope (P0 gate, curated):

    2. docs/index.md

    3. docs/core/GOVERNANCE.md
    4. docs/generated/control/NEXT_SESSION.md
    5. docs/generated/control/TRACEABILITY_SUMMARY.md
    6. docs_control/**/*.md

    7. musi byt PASS lokalne i v CI

    8. backlog scope (non-blocking):

    9. repo-wide **/*.md (seznam dluhu)

    10. slouzi pro mereni a burn-down, ne pro okamzite blokovani prace

    11. Backlog report se ma generovat samostatne a nesmi maskovat blokujici chyby v blocking scope.

    Vale scope policy (critical + changed-file + backlog)

    1. critical blocking (P0 gate, errors-only):

    2. docs/index.md

    3. docs/core/GOVERNANCE.md
    4. docs/generated/control/NEXT_SESSION.md
    5. docs/generated/control/TRACEABILITY_SUMMARY.md
    6. docs_control/next_session_note.md
    7. lokalne pres pre-commit hook vale-critical

    8. v CI jako samostatny Vale step

    9. changed-file blocking (errors-only):

    10. kazdy zmeneny .md soubor (krome explicitne vyloucenych generated/archive/vendor cest)

    11. lokalne pres pre-commit hook vale

    12. cil: novy dluh nevznika v menenych souborech

    13. repo backlog report + no-regression:

    14. repo-wide scan pres scripts/report_vale_backlog.ps1

    15. summary/log do logs/verify/*
    16. baseline v docs_control/vale_backlog_baseline.json
    17. verify_fast vynucuje no-regression (nesmi narust errors/warnings/suggestions)
    18. CI backlog step je non-blocking report vrstva

    Claim=evidence guard (batch status registry + preflight)

    1. docs_control/task_status.json je canonical registr batch/process claimu.

    2. kazdy batch ma status, required_artifacts, required_step_names

    3. status VERIFIED_* je povolen jen s last_verified.run_id

    4. evidence se overuje proti docs_control/verify_runs.json

    5. preflight se spousti pred dalsimi tvrzenimi o stavu:

    6. scripts/preflight_state_discovery.ps1

    7. generuje snapshot do logs/verify/preflight_state.json

    8. je report-only (rychly reality check)

    9. Capability audit gate je blokujici krok pred preflight pro tvrzeni o externim SW:

    10. docs_control/capability_audit.json (+ schema) = canonical registry capability claimu

    11. scripts/validate_capability_audit.ps1 = validator + evidence generator
    12. evidence: logs/verify/toolchain_capabilities.json + logs/verify/capability_audit_summary.json
    13. claim pouzity pro rozhodovani musi byt verified + mit oficialni zdroj

    14. bez auditu je status capability claimu unknown, ne kategoricky zaver

    15. Pred mutacnimi generatory/docs update kroky je povinny preflight write guard:

    16. scripts/assert_preflight_write_guard.ps1

    17. vyzaduje cerstve logs/verify/capability_audit_summary.json
    18. vyzaduje cerstve logs/verify/preflight_state.json + logs/verify/batch_status_verify_summary.json
    19. vyzaduje cerstve docs_control/observed_workflow/*.json (indexace reality)
    20. vynucuje poradi indexace/alignment -> capability audit -> preflight -> batch verify -> zmena

    21. vyjimka: render verify dashboarde z scripts/log_verify_run.ps1 muze pouzit -SkipPreflightWriteGuard, aby se neztratila evidence pri failu pred preflightem

    22. batch verifier je blokujici krok pro governance claimy:

    23. scripts/verify_batch_status.ps1

    24. FAIL pokud claim status > strojove odvozeny observed_status

    25. FAIL pokud VERIFIED_* nema platny run_id nebo required step PASS

    26. Volitelne zprisneni (pilot / vybrane batchy):

    27. verification.require_clean_worktree_for_verified = true

    28. VERIFIED_* claim je potom platny jen pri cistych batch artefaktech

    29. scripts/verify_batch_status.ps1 -ApplyAutoDowngrade muze automaticky snizit claim na IMPLEMENTED_UNVERIFIED, pokud jsou artefakty dirty

    30. Po zmene batch artefaktu se claim ma explicitne snizit na IMPLEMENTED_UNVERIFIED, dokud neni znovu dolozen PASS evidenci.

    31. Cilem je zabranit "epistemic drift":

    32. tvrzeni "je hotovo" bez cerstveho overeni reality

    33. zmena kontextu bez noveho preflight auditu

    Deterministicke pravidlo stavu (Spec-Kit + Superpowers)

    1. Stav PLANNED patri pouze do canonical docs_control/next_session.json (Markdown je jen generated view / narativ).

    2. Stav IMPLEMENTED je povolen az po dukazu:

    3. local hook PASS (pre-commit)

    4. CI PASS (ci.yml + quality-gate.yml)

    5. docs sync PASS (scripts/validate_workflow_alignment.ps1)

    6. Bez dukazu zustava stav ROZPRACOVANE nebo NEPROVEDENO.

    7. Tvrzeni "hotovo" bez PASS dukazu je governance poruseni (P0).
